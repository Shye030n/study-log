4) 개념
## 서브쿼리 = 쿼리 안의 쿼리
Q) "자유입출금통장 중에서 (잔액이 평균보다 많은 계좌)는?"

*** 서브쿼리는 1을 괄호 안에 쿼리로 넣어서, 1을 먼저 계산하고, 그 답을 2에 끼워넣게 하는 것.

JAVA로 치면 메서드의 반환값을 다른 식의 재료로 쓰는 것과 같다.
```
double avg = getAverageBalance("P001");         // 1 : 괄호 안쪽 쿼리
for (Account a : accounts) {                    // 2: 바깥 쿼리
    if (a.getBalance() > avg) result.add(a);    // 1 의 답을 조건에 사용
}
```
## 서브쿼리와 메인쿼리
    서브 쿼리 (=자식쿼리 =내부쿼리) : 메인쿼리 컬럼 사용 가능
    메인 쿼리 (=부모쿼리 =외부쿼리) : 서브쿼리 컬럼 사용 불가
: Java 객체지향의 상속과 같은 개념. 상속당한 자식 객체는 부모 객체의 인스턴스를 사용할 수 있고, 부모는 자식 객체의 인스턴스를 사용할 수 없다.

## 서브 쿼리의 장점
1. 쿼리를 구조화 시켜, 쿼리의 각 부분을 명확히 구분할 수 있게 함.
2. 복잡한 JOIN 이나 UNION과 같은 동작을 수행할 수 있는 또 다른 방법을 제공.
3. 가독성 좋음 (JOIN, UNION보다 읽기 편함)

### 서브쿼리의 위치에 따른 명칭
```
SELECT col1, (SELECT ...)   --스칼라서브쿼리: 하나의 컬럼처럼 사용, 조회용
FROM (SELECT ...)           --인라인뷰: 하나의 테이블처럼 사용, 테이블대체용
WHERE 채ㅣ = (SELECT ...)    --일반/중첩서브쿼리: 하나의 변수(상수)처럼 사용, 서브쿼리의 결과에 따라 달라지는 조건.
```

| 위치 | 이름 | 돌려줘야 하는 것 | 예 |
|---|---|---|---|
| WHERE 절, => 옆 | 단일행 서브쿼리| 값 1개 | > (SELECT AVG(...)) |
| WHERE 절, IN 옆| 다중행 서브쿼리 | 값 여러 개 (한 컬럼)| IN (SELECT CUST_NO ...) |
| WEHRE 절, EXISTS 옆| 존재 확인 | 행이 있/없는지만| EXISTS (SELECT 1 ...) |
| SELECT 절| 스칼라 서브쿼리 | 값 1개(행마다)| (SELECT COUNT(*) ...) AS 계좌수 |
| FROM 절 | 인라인 뷰 | 테이블처럼 쓸 결과 전체| FROM (SELECT ... GROUP BY ... ) T |

    - 모양이 다르면 에러.
    - 예를 들어 = 옆 서브쿼리가 2행을 돌려주면, 
    - ORA-01427:single-row subquery returns more than one row가 난다. 
    - (= 값 하나를 기대했는데, 여러개 값이 왔다) _ 현장에서 자주 보는 에러

상관 서브쿼리 : 바깥 행을 참조하는 서브쿼리
    - 대부분의 서브쿼리는 한 번만 계산하면 된다. 
    - (평균 잔액은 몇 번을 계산해도 동일하기에,)
    - 하지만, 서브쿼리 안에서 바깥 쿼리의 컬럼을 쓰면 얘기가 달라진다.

```
SELECT C.CUST_NM
    (
        SELECT COUNT(*)
        FROM ACCOUNT A 
        WHERE A.CUST_NO = C.CUST_NO 
        -- C는 바깥 쿼리
    )
FROM CUSTOMER C;
```
    - 여기서 안쪽의 C.CUST_NO 는 바깥 쿼리가 보고있는 객체.
    - 그래서 이 서브쿼리는 고객 한 명마다 한 번씩 다시 계산된다.
    => 이런 걸 상관 서브쿼리 (correlated) 라 한다.

자바로 보면
```
for (Customer c : customers) {  //바깥쿼리
    int cnt = countAccountsOf(c.getCustNo());   //안쪽쿼리
    resulta.add(new Row(c.getCustNm(), cnt));

}
```


5) 실무 연결 포인트
* 인라인 뷰 = 페이징 뼈대
    다음에 배울 Oracle ROWNUM 페이징은, "정렬한 결과를 인라인 뷰로 감싸고, 바깥에서 몇 번째부터 몇 번째까지 자른다"는 구조라서, 인라인 뷰를 모르면 읽을 수 없다. 거래내역 화면의 "다음 페이지"가 전부 이 구조다.
* 스칼라 서브쿼리는 현장에서 정말 많이 보인다.
    특히 코드값을 이름으로 바꿀 때, 
    (SELECT CD_NM 
    FROM 공통코드 
    WHERE CD = A.ACCT_STAT_CD) AS 계좌상태명
    다만, 바깥 행마다 실행되기에, 수십만 행을 조회하며, 스칼라 서브쿼리를 여러개 붙이면 성능 저하 생김
* NOT IN 은 NULL이 섞일 수 있는 컬럼에 쓰면 안됨.
    에러없이 결과가 0건이 되는 대표적인 조용한 버그. 
    "~가 없는 것"은 NOT EXISTS로 쓰는 습관을 들여야 안전
* 같은 결과를 JOIN, IN, EXISTS로 다 쓸 수 있다. 
    현장에선 이 셋이 섞여 나오기에, 어떤 모양이든 "결국 무엇을 구하는 쿼리인가"를 읽어낼 수 있어야 한다. 
    서브쿼리를 읽을 땐, 안쪽부터, 따로 떼어서 실행해보는 것이 가장 빠른 방법.
* ORA-01427 을 보면, "= 옆 서브쿼리가 여러 행을 돌려줬구나"라고 바로 떠올리면 됨.
    대부분 =를 IN으로 바꾸거나, 서브쿼리 조건이 덜 걸러진 걸 고치면 된다.
